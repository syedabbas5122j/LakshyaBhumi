TECHNICAL PROPOSAL AI-Enabled Geospatial Data Integration & Harmonization Platform In Response to the NAKSHA Programme — Multi-Source Land Data Integration Challenge Prepared for: Urban Land Administration & Cadastral Management Programme Domain: GeoAI · Spatial Data Engineering · Cadastral Systems Date: September 2026 Executive Summary Urban land administration under programmes such as NAKSHA depends on harmonizing spatial and non-spatial datasets generated by multiple departments and survey mechanisms — drone imagery, orthorectified imagery (ORI), DSM/DTM, ground truthing, GNSS/CORS surveys, municipal records, utility databases, and revenue land records. Today this harmonization is largely manual, GIS-analyst-driven, and error-prone. This proposal presents an AI-enabled Geospatial Data Integration Platform that automates the full lifecycle of multi-source land data — from ingestion and validation, through AI/ML-based spatial matching, automated topology correction, intelligent attribute mapping, and spatial conflict resolution, to confidence-scored, version-controlled, cadastral-ready outputs. The platform is designed so that the AI/GeoAI integration engine — the core innovation the programme is seeking — is a Phase 1 deliverable, not a later add-on, backed by production-grade ingestion, storage, ground-truthing, API, security, and monitoring infrastructure. The solution directly targets every outcome named in the problem statement: reduced manual GIS effort, improved record accuracy and consistency, seamless inter-departmental data exchange, faster cadastral finalization, and stronger interoperability across urban land information systems. 1. Background Urban land administration and cadastral management involve the integration of multiple spatial and non-spatial datasets generated from various departments, agencies, and survey mechanisms. Under modern land governance programmes such as NAKSHA, large volumes of geospatial data are being generated through drone surveys, orthorectified imagery (ORI), DSM/DTM datasets, ground truthing (GT), GNSS surveys, municipal records, utility databases, and revenue land records. At present, harmonization and integration of these datasets largely depend on manual GIS workflows, which are time-consuming and prone to errors. With the increasing availability of AI, GeoAI, and automated spatial processing technologies, there is significant scope to build an intelligent system capable of automatically integrating and synchronizing multi-source geospatial datasets with feature-extracted cadastral data. 2. Problem Statement 2.1 Objective Develop an AI-enabled geospatial integration platform capable of automatically integrating, harmonizing, validating, and synchronizing multiple land-related datasets with AI-generated feature extraction outputs. 2.2 Datasets to be Integrated Drone imagery • Orthorectified Imagery (ORI) • DSM/DTM datasets • Existing cadastral maps • Revenue records • Municipal GIS layers • Utility network data • Ground Truthing (GT) datasets • GNSS/CORS survey data • Building footprint datasets 2.3 Required Capabilities AI/ML-based spatial matching algorithms Automated topology correction Intelligent attribute mapping Geo-referencing and coordinate transformation engine Change detection mechanisms Spatial conflict resolution framework Confidence scoring for integrated outputs 2.4 Expected Outcomes Reduce manual GIS integration effort Improve accuracy and consistency of urban land records Enable seamless inter-departmental spatial data exchange Accelerate cadastral finalization processes Improve interoperability of urban land information systems Support standardized digital land governance 3. Proposed Solution Overview We propose a modular, cloud-deployable platform organized into five functional layers: (1) Multi-Source Ingestion & Validation, (2) Spatial Storage & Versioning, (3) an AI/GeoAI Integration Engine performing matching, topology correction, attribute mapping, geo-referencing, conflict resolution, and confidence scoring, (4) a Ground-Truthing loop that feeds corrections back into the models, and (5) Web/Mobile/API delivery for departments, surveyors, and citizens. The AI/GeoAI Integration Engine (Section 6) is the centerpiece of the platform and is scheduled for Phase 1, since it is the primary capability this programme is funding. All other modules exist to feed data into, and expose the outputs of, that engine reliably, securely, and at scale. 3.1 Solution Pillars Automated, AI-assisted integration rather than manual GIS conflation Confidence-scored outputs so reviewers focus effort where it matters Full version history and auditability across every dataset and correction API-first design for inter-departmental and third-party data exchange Field-verifiable via a mobile ground-truthing loop that retrains the matching models 4. System Architecture 4.1 Layered Architecture Layer Responsibility Key Components Ingestion Layer Accept, validate, and stage multi-source datasets Upload service, format/CRS validators, checksum & metadata extractors Storage Layer Durable, versioned, spatially-indexed storage MinIO/S3 (COG storage), PostgreSQL/PostGIS AI/GeoAI Engine Automated matching, correction, mapping, scoring Spatial matcher, topology corrector, attribute mapper, georeferencing service, conflict resolver, confidence scorer Ground Truth Loop Field verification & model feedback Mobile app, review workflow, retraining pipeline Delivery Layer Consumption by users & systems Web GIS viewer, REST/OGC APIs, dashboards, mobile app 4.2 Data Flow (Summary) Raw datasets (drone imagery, ORI, DSM/DTM, cadastral, revenue, municipal, utility, GT, GNSS/CORS, footprints) are ingested and validated. The Geo-referencing & Coordinate Transformation Engine normalizes every dataset to a common CRS. The AI/ML Spatial Matching module aligns features across sources; Automated Topology Correction resolves geometric errors. Intelligent Attribute Mapping reconciles schema and attribute differences across departments. The Spatial Conflict Resolution Framework auto-resolves low-severity conflicts and escalates the rest to ground truthing. Confidence Scoring is attached to every integrated feature and surfaced in the map viewer and API. Change Detection compares each new version against the current baseline and updates cadastral records, dashboards, and downstream systems. 4.3 Handling Large Geospatial Data Drone-survey and DSM/DTM datasets are routinely tens of gigabytes per site, and a state-wide cadastral layer can span millions of parcels. This section explains how the platform stays responsive without shipping full-resolution files to every client. 4.3.1 Client-Side: Stream Only What Is Visible Rasters (orthomosaics, DSM/DTM) are stored as Cloud-Optimized GeoTIFF (COG). The web map viewer and mobile app request only the tiles needed for the current zoom/pan window — typically kilobytes to a few megabytes — never the full file. Vector layers (cadastral boundaries, parcels, utility networks) are served as Vector Tiles (MVT), so the browser renders only the features in the visible extent, not the entire dataset. This is the same approach used by national and global imagery platforms (e.g., Bhuvan, Google Maps, Sentinel Hub) to keep multi-gigabyte datasets usable in a browser. 4.3.2 Server-Side: Where the Heavy Work Actually Happens Raw drone imagery, DSM/DTM generation, and ML model inference (feature matching, building-footprint extraction, topology correction) run entirely on backend/cloud compute — never in the browser or mobile client. Processed outputs are converted to COG/MVT once, at ingestion time, and cached — so the cost of handling a large file is paid once, not on every view. A CDN layer in front of tile endpoints absorbs repeat requests for commonly viewed areas, reducing load on the origin storage/database. 4.3.3 The Real Bottleneck: Field Upload, Not Viewing The genuine large-data challenge is uploading gigabytes from a drone survey site, often over poor rural connectivity — not displaying the data afterward. This is addressed directly in the Ingestion module: multipart upload for files over 100MB, resumable uploads that survive dropped connections, and a desktop uploader tool departments can run locally to stage and queue large transfers reliably. Physical drive ingestion and bulk server-folder scanning are also supported for sites where even resumable upload is impractical. 4.3.4 Storage Tiering Current/active versions stay on fast object storage for immediate access. Superseded versions move to a lower-cost archive tier via lifecycle policies, keeping full version history without paying premium storage costs indefinitely. 4.3.5 Where a Desktop Tool Still Helps GIS analysts doing intensive full-resolution editing (manual topology fixes, detailed ortho QA) benefit from a lightweight desktop tool or QGIS plugin that connects to the same backend — this complements the web app for that specific workflow rather than replacing it. Net effect: the web and mobile apps stay fast regardless of dataset size, because they never load full files — only the tiles in view. The actual size problem is handled once, at ingestion and upload, with tooling built specifically for that step. 5.
